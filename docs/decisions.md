# Decisions

The Action's design decisions, with the alternatives they were chosen
over. The first twelve are the questions of
[#1](https://github.com/marosoaie/steward-action/pull/1), answered by the
maintainer on 2026-10-27; all but 6 went as recommended. Swift-steward's
[docs/danger.md](https://github.com/marosoaie/swift-steward/blob/main/docs/danger.md)
section 8 holds the decisions this repository started from (decision 3: a
separate repository).

| # | Topic | Decision | Alternatives |
|---|---|---|---|
| 1 | Toolchain | The runner's Swift; swiftly when the runner has none or `swift-version` asks for another | Always install with swiftly, pinned in the Action; swift-actions/setup-swift; a `swift:<version>` container through `docker run` |
| 2 | `swift-version` | An input, Linux only; on macOS it's an error naming `xcode-select` and `DEVELOPER_DIR`, since swift.org toolchains there still need Xcode's SDK | No input: the runner image's Swift only |
| 3 | macOS | Supported with Xcode's Swift, and tested in CI | Ubuntu only, with build logs from other jobs |
| 4 | `product` | An input, defaulting to the template's `Dangerfile`, since Steward's options go after the product's name | Read it from `swift package describe --type json` |
| 5 | Report | Always `--report`, uploaded as `steward-report`; `report-artifact` renames it, and empty turns it off | No artifact, so a cut-short summary's pointer to it would be false |
| 6 | History | **Changed from the recommendation:** a shallow checkout gets the base and head commits' whole history (`git fetch --unshallow`, by SHA); a full clone fetches nothing. In the maintainer's words: "just fetch the whole history simpler and less error prone. We should avoid writing code if we can when the performance impact is not that big." | Deepening until the history passes a shell copy of Steward's `requireUncut` check (the recommendation); documenting `fetch-depth: 0` and fetching nothing |
| 7 | Event check | Any event but `pull_request` stops with exit 2 before the build | Leave it to Steward, a build later |
| 8 | `safe.directory` | The workspace is added to the global git config once, and stays for the job's later steps | `GIT_CONFIG_*` variables for the Action's steps only, which git reads for `safe.directory` only from 2.38 |
| 9 | Cache warming | Not now; a later `build-only` input could warm a `push` workflow's cache | Build it now |
| 10 | Fixture | This repository's own `Dangerfile/`, on swift-steward's `main` at the revision its `Package.resolved` pins, until a release has Steward; then `from:`. Since 0.1.0 (2026-11-03): `.upToNextMinor(from:)` Steward's latest minor release, as swift-steward's template does, since a 0.x minor release may break; 0.1.0, then 0.2.0 (#10, 2026-11-15), 0.3.0 (#12, 2026-11-18) and 0.4.0 (#16, 2026-11-20) | A separate test fixture; a revision pin in the manifest |
| 11 | Permission checks | Behind the `check-permissions` label, since every probe's comment notifies | On every pull request |
| 12 | Marketplace name | Decided later (step 5.3). `name: Steward` can't be listed, since `steward` is a GitHub user, and the name shouldn't say Swift: Steward checks projects in other languages too. The name doesn't affect `uses:` | |
| 13 | Pin updates | Dependabot's `github-actions` updates, monthly, grouped into one pull request, for `action.yml` and the workflows (2026-11-12) | Moving the pins by hand |
| 14 | Unfinished runs | Unless the Dangerfile ended with 0 or 1, a last step replaces the summary comment with fixed text saying Steward didn't finish: when it didn't build, crashed or exited with 2 (2026-11-18, the maintainer's "do it in the action"), or an earlier step failed (Fable's recommendation in review, not yet confirmed by the maintainer). It runs `scripts/crash-comment.js` with `actions/github-script`, since a `swift` container has no `curl`, `jq` or `python3`. `run.sh` runs Steward without `exec`, to write its status and start time; a comment written since that start, on GitHub's clock (the `Date` header less the time elapsed on the runner's), is left alone. A `swift run` that fails by itself with 1 reads as findings, and gets no such comment | Steward replacing it itself, which a Dangerfile that doesn't build or crashes can't; bash with `curl` and `jq`, posting nothing in a container; a Swift script run with the job's toolchain, which fails with it; only a failed build or run, leaving the comment stale when Swift's setup or the history fetch fails; the runner's clock alone |
| 15 | Releases | Made by `.github/workflows/release.yml`, run by hand from `main` with the version, and tagged `vX.Y.Z`, as in steward-lang-swift (2026-11-19, the maintainer's "Add the workflow where it's missing, and let's go with the V like you suggested"). Before tagging, it checks the version (`scripts/check-release-version.sh`, steward-lang-swift's) and that every pin in the README names the new tag (`scripts/check-readme-pins.sh`). It runs no tests: the Action is only tested by running it on a pull request; the ruleset requires CI's checks, though merges go through the maintainer's bypass (a review is required, and there's no second reviewer), so green checks at merge are practice, not a guarantee; and the pull request that moves the pins is the last merged before the release, up to date with `main` when its checks run, so they ran on the tree that's tagged | Calling `ci.yml` through `workflow_call`, whose jobs run the Action on a `pull_request` event and check results only a pull request gives, so they'd need a second mode; a step checking that the commit's pull request passed, which needs reads beyond `contents` on the writing job and, without the ruleset's up-to-date rule, still wouldn't be this tree's; the ruleset's "require branches to be up to date", the maintainer's to choose, which reruns CI on every open pull request after each merge; a job repeating the lint; tagging by hand |
